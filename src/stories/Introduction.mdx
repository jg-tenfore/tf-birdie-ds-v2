# ⛳ Birdie POS — Design System

A **React + MUI (Material UI) + Emotion** component library for the TenFore golf-course
point of sale, plus three working prototypes built from it.

This Storybook is the front door. Every other surface is a directory beside it:

## The three prototypes are one app

They are **not** three codebases. The only thing that differs is the course layout: the tee
sheet renders one column group per course, so a club's shape *is* its `courses` array. Each is
the same build run with a different `VITE_VENUE` — see `src/pos/data/venues.ts`.

<PrototypeLinks />

That matters because it is the same rule the prototype and this Storybook already follow: they
import the *same* components from `src/pos`, so refining a component changes all of them at
once. The original HTML is kept alongside so any drift from the source design is visible
rather than assumed.

Any prototype can also show another club without rebuilding — append `?venue=eighteen`,
`?venue=nine`, or `?venue=three-nines` to a deep link. See **Getting Started → Deep Links**.

## Design language

Ported from a prototype that follows **Material Design 3** role naming, so the token set is
MD3 — `primary` / `primary-container` / `on-surface` / `outline-variant` / `surface-container` —
and maps onto MUI's palette rather than living beside it. See **Foundations → Colors**.

Two things shape everything else:

- **Light mode only.** The POS runs on a lit pro-shop counter terminal. The tokens are
  semantic, so adding a dark scheme later means adding tones, not touching components.
- **Dense, not touch-first.** Controls sit at 12–14px with 1.5px outlines and ~32–38px hit
  targets, because an operator works this with a mouse across a fixed 1366×840 frame. (That's
  the opposite of the Goose KDS system this repo was scaffolded from, where gloved kitchen use
  forced everything large.)

## Structure

- **Foundations** — Colors, Typography, Spacing, Radius, Border, Effect Styles, Icons, Logos
- **Components** — grouped by purpose: **Actions**, **Navigation**, **Forms**,
  **Feedback & Status**, **Layout & Structure**, **Media & Visuals**, **Typography & Content**
- **Account** — Log in, Sign up, Forgot password, Verification
- **POS Screens** — the application itself, in seven sections:
  1. **Register & Order** — the catalog and the persistent order panel
  2. **Tee Sheet** — the courses × time grid, and its list view
  3. **Booking & Check-in** — the booking record and its five tabs
  4. **Tee Time Selection** — picking a slot, including 18-hole crossovers
  5. **Payment** — checkout, tips and change, the card reader
  6. **Operations** — blocks, notes, price overrides, leagues, moves
  7. **People** — member validation, golfer search, guest details

## How a screen story works

The whole app is driven by one reducer, so a screen is reproducible from a plain state
object. A story describes the state it wants and gets that screen — no clicking, no effects:

```tsx
<Screen initialState={withLoadedBooking(paidFoursome(), {
  modal: { kind: 'checkout' },
})} />
```

Pass `venueId` to render any of the three clubs the same way.

## Customizing

Everything renders inside `<ThemeProvider theme={theme}>`, so customization lives in two files:

- **`src/theme/tokens.ts`** — the token layer, ported 1:1 from the prototype's `:root` block.
  Nothing here imports MUI, so stories and plain CSS read the same values.
- **`src/theme/theme.ts`** — how those tokens map onto MUI's `palette`, `typography`, `shape`,
  and per-component `defaultProps` / `styleOverrides`.

Domain token groups hang off the palette: `palette.pay.*` (payment-state badges),
`palette.shifts.*` (time-of-day bands), `palette.memberTypes.*`, `palette.playerAccents`.

> Uses **core Material UI** plus **MUI X** — Data Grid and Date Pickers.
> `LocalizationProvider` (dayjs) is wired globally.
